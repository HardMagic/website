# Brief release evidence

`manifest.json` is generated by `scripts/generate-brief-pdfs.mjs` from `src/data/briefs.ts`.
It is the source-artifact evidence for the eight private editions, not proof of an Azure
upload, a live delivery path, or editorial approval.

## What the generator proves

- all eight brief IDs have a declared filename, version, edition date, source cutoff,
  page count, SHA-256 checksum, source register, and landing-page parity record;
- the rendered HTML source has a language attribute, semantic headings, captions,
  accessible figure names, a real table for the worksheet record, selectable text, and
  a linear reading order;
- Chromium is asked to emit tagged PDFs and document outlines, and the manifest records
  the observed tagged/outline markers;
- generated PDF creation/modification timestamps are normalized to the declared edition
  date, so the same source data produces stable PDF bytes and checksums;
- every normalized page has distinct text, has at least 45 words, and has no detected
  layout overflow;
- `storageVersion` and `uploadTime` remain `null`, and `deliveryState` remains
  `not-uploaded`.

The generated `.html` and `.pdf` files live in the ignored
`infra/brief-delivery/source-pdfs/` directory. If the HTML is used as an accessibility
alternative, it must be delivered behind the same exact-brief, private access control;
it is not a public fallback.

The current public brief route renders the shared title, thesis, promise, audience,
page count, chapter map, instruments, evidence, and limitations from the same data
objects. Edition/version, source-cutoff, brief ID, and topic-list fields are preserved in
the source and manifest but are not currently visible on that route; adding visible
publication-record metadata belongs to the route owner and is intentionally outside this
workstream.

## Required human and infrastructure work

The manifest is intentionally unsigned and marks `2026.08-draft` editions. A named
editorial reviewer must verify every page, citation link, figure description, contrast
choice, source cutoff, and PDF/UA screen-reader path before approval. The source records
identify direct primary-source URLs but do not claim that link status was checked.

Before any upload, the delivery owner must reconcile the three catalog titles that differ
from the landing data (`hybrid-ai-media-infrastructure`, `intelligent-media-asset-estate`,
and `modern-media-agency-transformation-playbook`) in the separately owned Function
catalog, or record an approved exception. Then an authorized release job must upload only
the reviewed files with Entra ID, capture the immutable Blob object version and upload
time, compare the stored bytes to each SHA-256, and run the exact-brief selection,
expiry, revocation, and superseded-edition canaries.

No Azure, Cloudflare, Front Door, email, storage, or Dataverse state is asserted by this
directory. Re-run the generator after any approved content change and treat the new
manifest as a new release candidate.
